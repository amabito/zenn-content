## はじめに

OSSへのPR提出は、初めての人には謎が多い。コードを書いて送ったら終わりではない。レビューされ、比較され、時には競合PRと並べて評価される。

OpenClaw（人気のCLIツール）へのPR #18762と#18763を提出した経験から、OSSコントリビューションの現実を書いておく。

---

## 何を直したか

Slack連携機能に軽微なバグがあった。転送されたメッセージ（forwarded attachment）を処理する際、認証ヘッダーが正しく渡されないケース。

修正自体は2行。

```diff
- const headers = buildHeaders(token)
+ const headers = buildHeaders(token, { includeAttachmentAuth: true })
```

シンプルな修正だからこそ、PRを出してみようと思った。「2行なら読まれやすいだろう」という考えもあった。

---

## 競合PRの登場

PR #18762を提出してしばらくすると、メンテナーからコメントが来た。

> "Thanks for the PR. There are a few similar PRs tackling this issue: #18704, #18762, #18763, #18881, #19203. We'll review them together."

似たような修正をしている人が複数いた。よくあることらしい。

BinHPdevというコントリビューターが#18704と#18881で同じ問題に取り組んでいた。そちらは修正範囲が広く、関連するエラーハンドリングも含めた包括的なアプローチだった。

---

## 比較の内容

メンテナーはPRを横並びで評価した。

| PR | アプローチ | スコープ |
|----|-----------|---------|
| #18704 (BinHPdev) | 包括的修正 | auth + error handling |
| #18762 (自分) | ポイント修正 | auth only |
| #18881 (BinHPdev) | 拡張版 | auth + tests + docs |
| #19203 (別の人) | 別解 | middleware approach |

自分のPR #18762は「point fix」と評された。悪い意味ではなく、スコープが小さすぎるという評価。

---

## 引いた理由

メンテナーから「スコープを広げてテストも追加できるか」という打診があった。

検討したが、断ることにした。

理由はいくつかある：

**1. 時間コストの非対称性**
2行の修正が、テスト追加・ドキュメント更新を含む大規模PRになる。工数が10倍以上になる。それを無償でやる理由が（今回は）薄い。

**2. BinHPdevが既によい仕事をしていた**
#18881は品質が高く、すでにテストも含んでいた。同じことを自分がやっても、コミュニティへの貢献量は増えない。

**3. 競合より補完を選ぶ**
同じ問題に複数の人が取り組んでいる場合、競争するより別の問題に取り組む方が生産的。

---

## PR #18762はクローズされた

「この問題はより包括的なPR #18881でカバーされるため」という理由でクローズ。

正直、最初はちょっと残念だった。でも振り返ると、これはOSSの正常な動作だと思う。

---

## PR #18763は今もオープン

#18763は別のエッジケースへの修正で、まだオープンなまま。stale noticeが来ている。

```
This PR has been inactive for 30 days. Please update or it will be closed.
```

これも現実。小さなPRは優先度が低く、放置されがち。

## 学んだこと

### OSSの現実1：競合PRは日常茶飯事

人気のプロジェクトでは、同じバグに気づく人が複数いる。特にドキュメントに書いてある既知のissueに対しては。「先に提出した」「より良い修正をした」という競争が普通に起きる。

### OSSの現実2：小さなPRは視認性が低い

2行のPRは読みやすいが、プロジェクトへの影響が小さい。メンテナーの優先度は必然的に低くなる。大きな修正を出すか、小さくても丁寧にコンテキストを書くか。

### OSSの現実3：引くことも戦略

競合PRが存在する場合、無理に競争しない方が良いケースがある。コミュニティ全体の効率を考えると、重複作業を減らす方が価値がある。

### OSSの現実4：一度出したPRは管理が必要

stale noticeが来たら何らかの対応が必要。コメントを更新するか、クローズするか。放置はあまり印象が良くない。

---

## 技術的な教訓（CI地獄について）

今回の反省は「1回のpushで全部直す」ということ。

最初、prettierの修正だけpushした。CIが30個以上のジョブを走らせて、TypeScriptエラーで落ちた。TypeScript修正してまたpush。今度はテストが落ちた。

結果的に4〜5回pushした。その都度、30個以上のジョブが走る。メンテナーのCI枠を無駄遣いしている感じがして居心地が悪かった。

以来、PRを出す前のチェックリストを作った：

```
[ ] prettier --check (全ファイル対象)
[ ] tsc --noEmit (TypeScriptエラーなし)
[ ] テスト実行 (ローカルで通ること)
[ ] コミットメールがGitHubアカウントに紐付いている
[ ] 全修正を1コミットにまとめた
```

これだけでpush回数を大幅に減らせる。

---

## OSSコントリビューションをどう位置づけるか

今回の経験から、自分の中でのOSSコントリビューションの位置づけが変わった。

「承認されること」を目標にすると消耗する。PRがクローズされたりstaleになったりは普通のことで、自分のコードが悪いわけではない。

「使っているツールへの返礼」「自分のコードを外部の目に晒す練習」くらいの感覚で続ける方が長続きする。

あとは単純に、コードレビューの過程で自分が気づかなかった問題点を指摘してもらえるのが勉強になる。今回も、メンテナーが「このケースも考慮したか？」と聞いてくれたことで、見落としに気づいた。

---

## まとめ

- 競合PRは普通。特に既知のissueには同時に複数の人が取り組む
- 小さなPRより、スコープを適切に広げた方がマージされやすい
- 引くことも選択肢。重複作業よりも別の問題に取り組む方が効率的
- push前のローカル検証は必須。CI枠の無駄遣いはコミュニティへの迷惑
- 「承認されること」より「参加すること」に価値を置く
