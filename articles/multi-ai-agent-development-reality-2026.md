## はじめに

「複数のAIエージェントを同時に使えば、開発速度は10倍になる」

2026年、Claude Code、GitHub Copilot、Gemini等、複数のAIコーディングツールが実用段階に入りました。

私は過去3ヶ月間、以下の構成で開発を進めてきました：

- **Claude Opus 4.6**: メイン開発環境（ファイル読み書き、ビルド、Git操作）
- **Claude Sonnet 4.5**: オーケストレーション（軽量タスク、ルーティング）
- **GPT-5.3 Codex**: コード生成特化（スタンドアロン）
- **Gemini 2.5 Pro**: 大規模コードベース分析・リサーチ（1M token context）

結論から言うと：**理想と現実には大きなギャップがありました**。

本記事では、3ヶ月の実運用で得た、マルチAIエージェント開発の**本当の姿**を共有します。

## 理想のマルチエージェント像

開発開始時、期待していたワークフロー：

```
User: "3DGS Rasterizerを最適化して"
  ↓
Sonnet (orchestrator): タスク分解
  ├─ Gemini: CUDA最適化手法をリサーチ
  ├─ Codex: 最適化コードを生成
  └─ Opus: コードを統合、ビルド、テスト
  ↓
完成！時間: 10分
```

**夢のような並列処理**で、人間は何もせずに完成すると思っていました。

## 現実のマルチエージェント運用

実際のワークフロー：

```
User: "3DGS Rasterizerを最適化して"
  ↓
Sonnet: タスク分解（5分）
  ↓
Gemini: CUDA手法リサーチ（10分）→ 1万文字のレポート
  ↓
User: Geminiの出力を読んで要点を整理（15分）
  ↓
Codex: コード生成（2分）→ 統合方法が不明
  ↓
User: Codexの出力を既存コードに手動統合（30分）
  ↓
Opus: ビルド→エラー（5分）
  ↓
Opus: デバッグ→修正→ビルド（20分）
  ↓
完成。時間: 87分
```

**ボトルネック**: AIエージェント間の**統合コスト**と**コンテキスト共有の困難さ**。

## 各AIエージェントの得意・不得意

3ヶ月の実運用で見えた、各AIの真の実力。

### Claude Opus 4.6（Tool統合型）

**得意なこと**:

- ✅ **反復的コード修正**（Read → Edit → Build → Fix loop）
- ✅ **ファイルシステム操作**（複数ファイル同時編集）
- ✅ **Gitワークフロー**（commit, PR作成、レビュー）
- ✅ **エラーからの自律回復**（ビルドエラー→原因特定→修正）

**不得意なこと**:

- ❌ **スタンドアロンコード生成**（既存コードに依存しすぎる）
- ❌ **大規模リファクタリング**（変更箇所が多いとミスが増える）
- ❌ **新規アルゴリズム実装**（既存パターンの組み合わせに留まる）

**コスト**: 1タスクあたり$0.50〜$2.00（Opusは高い）

**実例**:

```
User: "Phase 7-Bのstream compactionが遅い。最適化して"

Opus:
1. backward.cuを読む
2. ボトルネック特定（global atomics）
3. shared memory版に書き換え
4. ビルド→エラー（shared memory超過）
5. buffer sizeを削減
6. ビルド成功→テスト実行
7. ベンチマーク: 4.3 it/s → 86 it/s

完全自律で完了。時間: 35分
```

**Opusの真価**: Tool統合による**自律的なデバッグループ**。

### Claude Sonnet 4.5（軽量オーケストレーター）

**得意なこと**:

- ✅ **タスク分解とルーティング**（"これはCodexに", "これはOpusに"）
- ✅ **軽量コード編集**（<50行の変更）
- ✅ **ドキュメント生成**（README, CHANGELOG）
- ✅ **ファイル検索・情報収集**（Grep, Glob）

**不得意なこと**:

- ❌ **複雑な実装**（CUDA kernelは無理）
- ❌ **深い分析**（Opusに劣る）

**コスト**: 1タスクあたり$0.05〜$0.20（Opusの1/10）

**実例**:

```
User: "HyperRasterizerのREADME更新して"

Sonnet:
1. 既存README読む
2. 最新コードと差分確認
3. 新機能セクション追加
4. ビルド手順更新
5. 完了

時間: 3分
```

**Sonnetの真価**: **低コストで大量の軽作業を処理**。

### GPT-5.3 Codex（コード生成特化）

**得意なこと**:

- ✅ **スタンドアロンコード生成**（新規関数、クラス）
- ✅ **アルゴリズム実装**（既知パターンの高速実装）
- ✅ **コードレビュー**（静的解析的な指摘）
- ✅ **一発生成**（完成度が高い）

**不得意なこと**:

- ❌ **既存コードの理解**（ファイル読み込み機能なし）
- ❌ **反復修正**（エラーフィードバックループなし）
- ❌ **ビルド・テスト**（Tool統合なし）

**コスト**: 1タスクあたり$0.10〜$0.30（安い）

**実例**:

```bash
# Codex CLIでコード生成
codex exec --model gpt-5.3-codex --sandbox read-only --full-auto \
  "CUDAでWarp-level reduction実装して。FP16対応。Shared memory使用。"

# 出力: 完璧なCUDAカーネル（200行）
# 問題: 既存コードへの統合方法は不明
```

**Codexの真価**: **新規コードの高速・高品質生成**。既存コードとの統合は人間の仕事。

### Gemini 2.5 Pro（大規模分析・リサーチ）

**得意なこと**:

- ✅ **大規模コードベース理解**（1M token context = 約30万行）
- ✅ **技術リサーチ**（Google Search grounding）
- ✅ **マルチモーダル処理**（PDF, 動画, 音声からの情報抽出）
- ✅ **アーキテクチャ俯瞰**（依存関係、設計パターン抽出）

**不得意なこと**:

- ❌ **コード生成**（Claude/Codexに劣る）
- ❌ **ファイル編集**（Tool統合なし）
- ❌ **即時性**（レスポンスが遅い：20〜60秒）

**コスト**: 1タスクあたり$0.30〜$1.50（長文出力で高額化）

**実例**:

```bash
gemini -p "HyperRasterizer全体のアーキテクチャを分析して。ボトルネックと改善案を提案" \
  --include-directories D:/work/Projects/3dgs-unified/src/hyper_rasterizer

# 出力: 5000行のMarkdownレポート
# - ファイル構造図
# - データフロー解析
# - 8個のボトルネック特定
# - 各ボトルネックの改善案（コード例付き）

# 問題: 出力が長すぎて読むのに30分かかる
```

**Geminiの真価**: **人間が把握できないスケールのコード理解**。出力の消化が課題。

## アンチパターン：やってはいけないこと

実際に失敗した運用パターン。

### 1. Opusを全タスクに使う

**症状**: コスト爆発。

```
初期（Opus 80%）:
- 1日のコスト: $45〜$60
- Opusトークン消費: 300K〜500K tokens/day
```

**原因**: 軽量タスク（ファイル検索、ドキュメント更新）もOpusで実行。

**対策**: Sonnetにルーティング。

```
改善後（Opus 15%）:
- 1日のコスト: $12〜$18（-70%）
- Sonnetが軽作業を80%担当
```

### 2. Codexに全てを任せる

**症状**: 統合コストが生成コストを超える。

```
Codex生成時間: 2分
統合作業時間: 45分（手動でコピペ、変数名修正、import追加）

総時間: 47分
Claude Opusに任せた場合: 20分
```

**教訓**: Codexは**新規コード生成のみ**に使う。既存コード修正はOpus/Sonnetが速い。

### 3. 複数エージェントの同時並列実行

**期待**:

```
Task A (Opus) + Task B (Codex) + Task C (Gemini) = 3倍速
```

**現実**:

```
Task A (Opus): コンテキスト A
Task B (Codex): コンテキスト B（Aと共有不可）
Task C (Gemini): コンテキスト C（A, Bと共有不可）

統合作業: 人間が3つのコンテキストを手動マージ（60分）
```

**教訓**: 並列実行は**独立したタスク**のみ。依存関係があるタスクは逐次実行。

### 4. コンテキストをキャッシュしない

**症状**: 同じファイルを何度も読み込む。

```
Opus: config.cu読む（2K tokens）
Codex: config.cu読む（2K tokens）
Gemini: config.cu読む（2K tokens）

合計: 6K tokens浪費
```

**対策**: 共通ファイルは`.claude/docs/`に要約を保存。

```
.claude/docs/codebase-summary.md
.claude/docs/cuda-kernel-patterns.md

各エージェント: 要約を参照（500 tokens）
```

### 5. Gemini出力の丸呑み

**症状**: Geminiが5000行のレポートを生成。読む時間が1時間。

**対策**: 出力形式を制限。

```bash
# Before
gemini -p "分析して"

# After
gemini -p "分析して。出力は以下のフォーマット:
1. 問題点（箇条書き、5個以内）
2. 改善案（各100文字以内）
3. 優先度（High/Med/Low）
合計500文字以内"
```

**結果**: 出力1/10、読む時間5分。

## 実際のワークフロー：動く構成

3ヶ月の試行錯誤で落ち着いた、**実用的な**マルチエージェント構成。

### 基本方針

```
Sonnet: セッション本体（オーケストレーター）
  ├─ 軽作業: 自分で処理
  ├─ 重い実装: Task(model="opus")
  ├─ コード生成: Codex CLI
  └─ リサーチ: Gemini CLI
```

### タスク分類フローチャート

```
タスク到着
  ↓
Q: コード50行以上書く？
  Yes → Task(model="opus")
  No  ↓
Q: 新規アルゴリズム？
  Yes → Codex CLI
  No  ↓
Q: 設計判断・トレードオフ評価？
  Yes → Codex CLI（レビューモード）
  No  ↓
Q: 大規模コード分析・最新技術調査？
  Yes → Gemini CLI
  No  ↓
Sonnet（自分で処理）
```

### 実例：Phase 7-B Stream Compaction最適化

**タスク**: HyperRasterizer Backward kernelの高速化（4.3 it/s → 80+ it/s）

**実際のフロー**:

```
[Step 1] User → Sonnet
"backward kernelが遅い。最適化して"

[Step 2] Sonnet → Gemini（リサーチ）
"CUDA stream compactionの最新手法を調査"
→ 出力: CUB, Thrust, Custom implementationの比較レポート（500行）

[Step 3] Sonnet → 要約作成
Gemini出力から3つの改善案を抽出:
1. Global atomics削除
2. Shared memory compaction
3. Warp-level reduction

[Step 4] Sonnet → Task(model="opus")
"backward.cuのglobal atomicsをshared memory版に書き換え"

[Step 5] Opus（実装）
- backward.cu読む
- 修正実装
- ビルド→エラー（shared memory超過）
- buffer削減
- ビルド成功
- ベンチマーク: 4.3→86 it/s

[Step 6] Sonnet → Codex（レビュー）
"この修正を批評して"
→ 出力: "Occupancy低下のリスク。__launch_bounds__調整推奨"

[Step 7] Opus（最終調整）
__launch_bounds__(256, 2) → (256, 4)
ベンチマーク: 86→92 it/s

完了。時間: 50分
```

**各エージェントの役割**:

- Sonnet: オーケストレーション（10分）
- Gemini: リサーチ（10分）
- Opus: 実装・デバッグ（25分）
- Codex: レビュー（5分）

**もしOpus単独なら**: 90分（リサーチに時間がかかる）
**もしCodex単独なら**: 不可能（反復デバッグができない）

```

### 移行後（適材適所）

```

1. **軽作業のSonnet移行**: $24/day削減
2. **新規コード生成のCodex化**: $12/day削減
3. **リサーチのGemini集約**: $2/day削減

**重要**: 速度は落ちていない。むしろ15%向上（適材適所で効率化）。

## 結論：マルチエージェントの真価

### 理想

「複数AIが協調して、人間不要で完成」

### 現実

「各AIが得意分野を担当。人間はオーケストレーション」

### 真の価値

**人間のボトルネックを各AIが分担して解消**。

- ビルド・デバッグループ → Opus
- 大規模コード理解 → Gemini
- 新規コード生成 → Codex
- タスク分解・軽作業 → Sonnet

**結果**: 開発速度2.5倍、コスト-63%、品質向上（レビュー自動化）。

### 10倍にならなかった理由

1. **統合コスト**: AI間のコンテキスト共有が困難
2. **並列化の限界**: 依存タスクは逐次実行
3. **出力の消化**: Geminiの長文レポートを読む時間
4. **判断の最終責任**: 設計判断は人間が必要

### それでも十分価値がある

**1人で3人分の仕事ができる**。

従来:
- 実装（自分）
- レビュー（同僚）
- リサーチ（自分）

現在:
- 実装（Opus）
- レビュー（Codex）
- リサーチ（Gemini）
- 統合・判断（自分）

**この分業が、現実的なマルチエージェント開発の姿**です。
