# 失敗パターン17選と対策

## 【経営層の問題】

### 1. 「DX=最新システム導入」という誤解

```
症状:
「AIを入れろ」「クラウド化しろ」が目的化
→ 何のためにやるのか不明確

対策:
「何を解決したいのか」を先に明確化
システムはあくまで手段

説得テンプレート:
「DXの目的は〇〇の課題解決です。
 システムはそのための手段の1つです。
 まず課題の優先順位を決めませんか？」
```

### 2. 投資対効果を求めすぎる

```
症状:
「ROIは？」「何年で回収？」
→ 数字を出せない小さな改善が却下される

対策:
段階的な投資と効果測定を提案
「まず100万円で試して、効果があれば拡大」

説得テンプレート:
「まず小規模に試験導入し、3ヶ月で効果測定します。
 効果があれば本格展開、なければ撤退します。
 リスクを最小化しながら進めましょう。」
```

### 3. 短期で結果を求める

```
症状:
「3ヶ月で効果を出せ」
→ 無理な計画 → 失敗

対策:
短期・中期・長期の目標を分けて設定

説得テンプレート:
「短期（3ヶ月）: 日報デジタル化 → 効果測定
 中期（6ヶ月）: 工程管理デジタル化
 長期（1年）: 全社展開
 段階的に進めることで確実に成果を出します。」
```

### 4. 現場を知らない意思決定

```
症状:
経営層が「これがいい」と決めたシステムが
現場のニーズと合っていない

対策:
現場ヒアリングを必須プロセスに

説得テンプレート:
「導入前に現場の意見を聞かせてください。
 現場が使いたいと思わないシステムは定着しません。
 ヒアリングに1週間いただけますか？」
```

## 【現場の問題】

### 5. 「今のままでいい」症候群

```
症状:
「30年これでやってきた」
「新しいことを覚える時間がない」

対策:
現状の課題を「自分ごと」にさせる

説得テンプレート:
「〇〇さん、毎月の報告書作成に何時間かかってますか？
 （答え: 10時間）
 これが1時間になったら、空いた時間で何したいですか？」
```

### 6. ITアレルギー

```
症状:
「パソコン苦手」「機械は信用できない」

対策:
スマホアプリから始める（スマホは使えることが多い）

説得テンプレート:
「スマホで写真撮るのは得意ですよね？
 それだけでOKです。あとは自動でやります。」
```

### 7. 「また新しいこと」疲れ

```
症状:
過去に失敗したDXの記憶
「どうせまた使われなくなる」

対策:
過去との違いを明確に示す

説得テンプレート:
「前回は全社一斉導入で混乱しました。
 今回は〇〇さんの現場だけで試します。
 うまくいかなければすぐやめます。」
```

### 8. 声の大きい反対者

```
症状:
ベテランの1人が強く反対
→ 周りも追従

対策:
その人を最初に巻き込む or 別の人から始める

説得テンプレート（巻き込む場合）:
「〇〇さんの意見を聞かせてください。
 〇〇さんが『これならいける』と言えば、
 みんな安心します。」
```

## 【技術・システムの問題】

### 9. オーバースペック

```
症状:
多機能すぎて誰も使いこなせない

対策:
必要最小限の機能に絞る
「将来使うかも」は後回し

チェックリスト:
□ 80%のユーザーが使う機能だけに絞ったか
□ 「あったら便利」は除外したか
□ 操作ステップは3つ以内か
```

### 10. 現場のインフラ無視

```
症状:
現場にWi-Fiがない
スマホの電波が入らない

対策:
事前のインフラ調査を必須に

チェックリスト:
□ 現場の通信環境を確認したか
□ オフライン対応は必要か
□ 充電環境はあるか
```

### 11. 既存システムとの連携不足

```
症状:
新システムと旧システムでデータが分断
二重入力が発生

対策:
既存システムとの連携を最初から設計

チェックリスト:
□ 既存システム一覧を作成したか
□ データ連携方法を検討したか
□ 移行計画を立てたか
```

## 【体制・プロセスの問題】

### 12. 推進担当者が孤立

```
症状:
DX担当が1人で頑張る
→ 周りは傍観

対策:
経営層のコミットメントを明確に

説得テンプレート:
「DXを成功させるには、経営層の〇〇さんから
 全社に『これは重要』と発信していただけますか？
 現場は上の本気度を見ています。」
```

### 13. 予算はあるが人がいない

```
症状:
「予算1000万円つけた」
でも担当者は通常業務と兼任

対策:
専任担当 or 外部リソースを確保

説得テンプレート:
「DXは片手間では進みません。
 〇〇さんの工数を50%確保するか、
 外部から支援を入れる必要があります。」
```

### 14. ベンダー丸投げ

```
症状:
「よくわからないからベンダーに任せた」
→ 現場のニーズと乖離

対策:
社内に「わかる人」を育てる

説得テンプレート:
「ベンダーは技術のプロですが、御社の業務は知りません。
 社内で業務を理解している人を窓口にしてください。
 私が一緒に伴走します。」
```

### 15. 効果測定をしない

```
症状:
「なんとなく便利になった気がする」
→ 次の予算が取れない

対策:
導入前にKPIを設定

KPI例:
- 作業時間: 導入前〇時間/月 → 導入後〇時間/月
- エラー件数: 導入前〇件/月 → 導入後〇件/月
- 残業時間: 導入前〇時間/月 → 導入後〇時間/月
```

## 【その他】

### 16. 成功事例の盲信

```
症状:
「A社がやってるから」
→ 自社の状況を考慮しない

対策:
成功事例の「前提条件」を確認

チェックリスト:
□ A社と自社の規模は近いか
□ A社と自社の業務フローは近いか
□ A社の成功要因は自社でも再現可能か
```

### 17. 「完璧」を求めすぎる

```
症状:
「もっと検討してから」
→ いつまでも始まらない

対策:
「まず試す」文化を作る

説得テンプレート:
「100点を目指して1年検討するより、
 60点で始めて改善する方が早く成果が出ます。
 まず1ヶ月試してみませんか？」
```

# DXロードマップテンプレート

## Phase 1: 準備（1-2ヶ月）

```
Week 1-2: 現状把握
- 業務フローの可視化
- 課題のヒアリング
- キーパーソンの特定

Week 3-4: 計画策定
- 優先順位付け
- 最初の対象業務を選定
- KPI設定

Week 5-8: 体制構築
- 経営層のコミットメント獲得
- 推進担当のアサイン
- 予算確保
```

## Phase 2: 試験導入（2-3ヶ月）

```
Week 1-2: ツール選定
- 候補ツールの比較
- トライアル実施
- 現場フィードバック

Week 3-6: 試験導入
- 1つの現場で開始
- 並行運用
- 問題点の洗い出し

Week 7-12: 効果測定
- KPI測定
- 改善点の特定
- 横展開計画の策定
```

## Phase 3: 本格展開（6-12ヶ月）

```
Month 1-3: 横展開（グループ1）
- 成功パターンの標準化
- 次の現場へ展開
- サポート体制の整備

Month 4-6: 横展開（グループ2-3）
- さらに範囲を拡大
- 社内ノウハウの蓄積

Month 7-12: 定着化
- 運用ルールの確立
- 次のDXテーマの検討
- 継続的改善の仕組み化
```
