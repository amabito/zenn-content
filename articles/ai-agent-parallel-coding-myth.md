# 結論から言う

**並列コーディングエージェントは「銀の弾丸」ではない。Stanfordの研究はそれを証明し、筆者の1万行超CUDAプロジェクト開発の実体験も同じ結論に至った。**

「AIエージェントを10台並列で走らせれば10倍速くなる」という期待は幻想だ。METR（Model Evaluation & Threat Research）のランダム化比較試験では、AI利用時に開発者のタスク完了が19%遅くなった。Stanford・Harvardの研究は、エージェントがデモでは輝くが実運用で崩壊する原因を特定した。

しかし、AIコーディングエージェントが無意味なわけではない。**使い方を間違えているだけだ。**

**この記事で得られること:**
- 並列エージェントが失敗する科学的根拠
- 1万行超CUDAプロジェクトでのClaude Code実体験
- 有効なエージェント活用パターン（Skill、Hook、MCP）

# 研究が示す「並列の幻想」

## METR研究：AIを使うと19%遅くなった

2025年7月、METRが実施したランダム化比較試験（RCT）の衝撃的な結果。

### 実験条件

- **被験者**: 経験豊富なOSS開発者16名
- **タスク数**: 246タスク
- **対象リポジトリ**: 被験者が平均5年以上関わったプロジェクト
- **使用ツール**: Cursor Pro、Claude 3.5/3.7 Sonnet
- **手法**: 各タスクをランダムにAI許可/不許可に割り当て

### 結果

| 指標 | 数値 |
|------|------|
| 開発者の事前予測 | AI利用で24%速くなる |
| 事後の主観評価 | AI利用で20%速くなった（と感じた） |
| **実測値** | **AI利用で19%遅くなった** |

**主観と実測の乖離が43ポイント。** 開発者は「速くなった」と感じながら、実際には遅くなっていた。

### なぜ遅くなったのか

1. **レビューコスト**: AI生成コードの44%以上が不採用。採用分も56%が大幅修正必要
2. **コンテキスト不足**: リポジトリに精通した開発者ほど遅くなった（AIが既存コードの暗黙知を理解できない）
3. **過信バイアス**: AI出力を信頼しすぎて検証が甘くなる

## Stanford・Harvard研究：エージェントが実運用で崩壊する理由

2025年12月の論文が特定した根本原因。

**「エージェントは知性が足りないから失敗するのではない。適応できないから失敗する。」**

### 3つの崩壊パターン

1. **計画実行型の限界**: ほとんどのエージェントは「計画を実行する」設計であり「計画を修正する」設計ではない
2. **前提の固定化**: 世界が安定していると仮定し、現実の変化に対応できない
3. **盲目的前進**: 前提と現実が乖離しても、立ち止まらずに推し進める

### 並列の本質的問題

```
並列エージェントの理想:
  タスクA → エージェント1 → 結果A
  タスクB → エージェント2 → 結果B  → 統合 → 完成
  タスクC → エージェント3 → 結果C

現実:
  タスクA → エージェント1 → 結果A（Bと競合する変更）
  タスクB → エージェント2 → 結果B（Aと矛盾）→ 人間がマージ → コンフリクト地獄
  タスクC → エージェント3 → 結果C（A+Bの前提で作業すべきだった）
```

ソフトウェアは本質的に状態を共有するシステムだ。並列化できるのは「本当に独立した」タスクだけであり、それは全体のごく一部にすぎない。

## Faros AIの大規模調査

10,000人以上の開発者、1,255チームの分析結果。

- AI導入チームはタスク数が9%増、PR数が47%増
- しかし**コンテキストスイッチの増加**が生産性を相殺
- 「AIが並列で足場を組める」→「開発者がオーケストレーションに時間を取られる」

# 実体験：1万行CUDAプロジェクトでのClaude Code

## プロジェクトの規模

筆者はHyperRasterizer（3DGS用CUDAラスタライザ）とHyperSplat（学習フレームワーク）をClaude Codeで開発してきた。

| 指標 | 数値 |
|------|------|
| CUDAコード行数 | 1万行超 |
| Python（学習フレームワーク） | 数千行 |
| バージョン反復回数 | v2〜v22（10回以上の作り直し） |
| 使用LLM | Claude Opus 4.5（メイン） |

## 並列エージェントを試した結果

### 試したこと

Claude Codeで複数のサブエージェントを並列起動し、異なるモジュールを同時開発。

### 失敗したパターン

**1. CUDAカーネルの並列開発**
- Forward PassとBackward Passを別エージェントで開発
- 結果: 共有メモリのレイアウト前提が食い違い、全面的に書き直し
- 教訓: **密結合なコンポーネントは並列化不可能**

**2. ラスタライザ + 学習フレームワークの同時修正**
- ラスタライザのAPI変更と学習フレームワークの対応を並列実行
- 結果: APIシグネチャの不整合。コンパイルすら通らない
- 教訓: **インターフェースをまたぐ変更は逐次的にやるべき**

**3. 複数バリエーションの同時実装**
- 最適化手法のバリエーションA/B/Cを並列で実装
- 結果: 共通ユーティリティの重複実装、マージ不可能
- 教訓: **共有基盤がある場合、並列は逆効果**

### 成功したパターン

**1. ドキュメント生成と実装の並列**
- エージェント1がコード実装、エージェント2がAPI仕様書を先行作成
- 結果: 実装完了時にドキュメントも完成
- 成功理由: **真に独立したタスク**

**2. テスト作成の並列化**
- ユニットテストを機能単位で別エージェントに割り当て
- 結果: テストカバレッジが短時間で向上
- 成功理由: **テストは他のテストに依存しない**

**3. 異なるプロジェクトの同時作業**
- HyperRasterizerのバグ修正とZenn記事の執筆を並列
- 結果: 待ち時間の有効活用
- 成功理由: **完全に別のコンテキスト**

# 有効なエージェント活用法

## 並列ではなく「深化」

METR研究で示された「19%遅くなる」は、エージェントを「速度向上ツール」として使った場合の話だ。

**エージェントの真価は「速度」ではなく「到達点」にある。**

```
Without AI: 1時間で80%の品質のコードを書く
With AI:    1.2時間で95%の品質のコードを書く（19%遅いが品質は向上）
```

筆者のHyperRasterizer開発では、Claude Codeなしでは到達できなかった最適化レベルに達した。速度は目的ではない。

## Claude Codeの実践的ワークフロー

### 1. Skill：再利用可能なワークフロー定義

```
使い方:
├── プロジェクト固有のSkillを定義
├── 「HyperRasterizerのビルド→テスト→ベンチマーク」を1コマンドで実行
└── 繰り返しタスクの自動化
```

**効果**: 同じ手順を毎回説明する必要がなくなる。エージェントの文脈理解コストを削減。

### 2. Hook：自動品質ゲート

```
使い方:
├── コミット前にリンター実行
├── ファイル保存時に自動フォーマット
└── ビルドエラー時の自動修復トリガー
```

**効果**: AIの出力を自動的に品質チェック。METR研究が指摘した「検証コスト」を削減。

### 3. MCP：外部ツール統合

```
使い方:
├── GitHub Issues/PRとの連携
├── ビルドシステムとの統合
└── カスタムツール（ベンチマーク実行等）の呼び出し
```

**効果**: エージェントが開発環境全体を理解して作業できる。コンテキスト不足の問題を軽減。

### 4. CLAUDE.md：暗黙知の明文化

```
効果:
├── プロジェクト固有のルールを事前にエージェントに共有
├── 「なぜそう設計したか」をCLAUDE.mdに記録
└── 新しいセッションでもコンテキストが失われない
```

**これがMETR研究の「暗黙知問題」への直接的な解答。** リポジトリに精通した開発者が遅くなったのは、AIがその暗黙知を持たないからだ。CLAUDE.mdはその知識を明文化する仕組みだ。

# 2026年のAI開発のリアル

## やるべきこと

1. **逐次的に、深く使う**: 並列ではなく、1つのタスクにエージェントと集中的に取り組む
2. **暗黙知を明文化する**: CLAUDE.mdにプロジェクトの設計思想・制約・過去の失敗を記録
3. **自動品質ゲートを設ける**: Hookでリンター・テスト・フォーマットを自動実行
4. **独立タスクだけ並列化する**: テスト生成、ドキュメント、別プロジェクトなど

## やってはいけないこと

1. **密結合コンポーネントの並列開発**: 必ずコンフリクトが起きる
2. **AI出力の無条件採用**: 56%は大幅修正が必要という研究結果
3. **速度を目的にする**: 到達点の向上が真の価値
4. **主観的な体感を信じる**: 43ポイントの乖離がある

# まとめ

| 観点 | 結論 |
|------|------|
| 並列エージェント | ソフトウェアの本質的な状態共有により、ほとんどのタスクで失敗する |
| 速度向上 | AI利用で19%遅くなるという実測データあり（METR研究） |
| 真の価値 | 速度ではなく到達点。AIなしでは不可能だった品質レベルへの到達 |
| 有効な使い方 | Skill/Hook/MCP/CLAUDE.mdによる文脈共有と品質自動化 |
| 1万行CUDAでの実感 | 並列は失敗、逐次的な深い対話が最も効果的 |

**AIコーディングエージェントは「人数」ではなく「深度」で使え。** 並列エージェントの幻想を捨て、1つのエージェントと深く協働することが、2026年のAI開発の最適解だ。
