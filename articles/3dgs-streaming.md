# 結論から言う

**大規模な3DGSシーンも、ストリーミング技術で快適に配信できる。**

| 手法 | 初期読み込み | メモリ使用 | 品質 |
|------|-------------|-----------|------|
| 全読み込み | 30秒 | 500MB | 最高 |
| LODストリーミング | 3秒 | 50MB〜 | 段階的向上 |
| 視点ベース | 2秒 | 100MB | 最高（視野内） |

この記事では、3DGSの効率的な配信手法を解説する。

---

# なぜストリーミングが必要か

## 3DGSの課題

```
大規模シーンの問題:
├── ファイルサイズ: 100MB〜1GB
├── 読み込み時間: 数十秒〜数分
├── メモリ消費: VRAM + システムRAM
└── モバイルでは表示不可能

ユーザー体験:
├── 3秒以上の待機で離脱率急増
├── モバイルユーザーを逃す
├── 「重いサイト」の印象
└── ビジネス機会の損失
```

## ストリーミングの効果

```
ストリーミング導入後:
├── 初期表示: 2-3秒
├── 段階的に品質向上
├── 必要な部分だけ読み込み
└── モバイルでも快適
```

---

# 手法1: LODストリーミング

## 概念

```
LOD (Level of Detail):
├── 複数の詳細度バージョンを用意
├── 低解像度 → 高解像度の順で配信
├── 即座に「何か」が表示される
└── 徐々に品質が向上

流れ:
1. LOD0（低）: 5MB、1秒で表示
2. LOD1（中）: 20MB、追加3秒
3. LOD2（高）: 100MB、追加10秒
4. LOD3（最高）: 500MB、バックグラウンド
```

## 実装イメージ

```
サーバー側:
├── scene_lod0.ply (5MB) - 10K Gaussians
├── scene_lod1.ply (20MB) - 50K Gaussians
├── scene_lod2.ply (100MB) - 250K Gaussians
└── scene_lod3.ply (500MB) - 1M Gaussians

クライアント側:
├── LOD0をリクエスト → 即座に表示
├── LOD1をバックグラウンドで取得
├── 取得完了 → LOD0からLOD1に切り替え
└── 以降繰り返し
```

## 効果

| 指標 | 全読み込み | LODストリーミング |
|------|-----------|------------------|
| 初期表示 | 30秒 | 1秒 |
| 完全表示 | 30秒 | 15秒（段階的） |
| 離脱率 | 高い | 低い |

# 手法2: 視点ベースストリーミング

## 概念

```
視点ベース:
├── ユーザーが見ている方向のみ配信
├── 視野外のGaussianは遅延読み込み
├── カメラ移動を予測してプリフェッチ
└── メモリ効率が最高

流れ:
1. 初期視点のGaussianを取得（10%）
2. ユーザーがカメラを動かす
3. 新しい視野のGaussianを追加取得
4. 視野外のGaussianをアンロード（オプション）
```

## 空間分割

```
シーンを空間分割:
├── Octree（八分木）で分割
├── 各ノードに含まれるGaussianを記録
├── 視錐台（Frustum）と交差するノードを特定
└── 交差するノードのGaussianのみ取得

例:
├── 全体: 1M Gaussians (500MB)
├── 現在の視野: 100K Gaussians (50MB)
└── メモリ節約: 90%
```

## 効果

| 指標 | 全読み込み | 視点ベース |
|------|-----------|-----------|
| 初期メモリ | 500MB | 50MB |
| 最大メモリ | 500MB | 100-200MB |
| 初期表示 | 30秒 | 2秒 |

---

# 手法3: タイルベースストリーミング

## 概念

```
タイルベース:
├── シーンを固定サイズのタイルに分割
├── ユーザー位置に基づいてタイルを読み込み
├── 遠いタイルは低LOD、近いタイルは高LOD
└── Google Mapsのタイル配信に近い概念

利点:
├── キャッシュ効率が良い
├── CDN配信に適している
├── 複数ユーザーで共有可能
└── 実装がシンプル
```

## 構造

```
tiles/
├── z0/                    # ズームレベル0（全体）
│   └── 0_0.ply
├── z1/                    # ズームレベル1
│   ├── 0_0.ply
│   ├── 0_1.ply
│   ├── 1_0.ply
│   └── 1_1.ply
├── z2/                    # ズームレベル2（詳細）
│   ├── 0_0.ply
│   ├── ...
│   └── 3_3.ply
└── metadata.json          # タイル情報
```

# プロトコル設計

## リクエスト/レスポンス

```
クライアント → サーバー:
{
  "type": "request_gaussians",
  "viewport": {
    "position": [10, 5, 3],
    "direction": [0, 0, -1],
    "fov": 60
  },
  "quality": "medium"
}

サーバー → クライアント:
{
  "type": "gaussian_data",
  "count": 50000,
  "data": <binary>,
  "next_chunk": "/api/chunk/xyz123"
}
```

## 帯域適応

```
帯域検出:
├── 初期: 低品質で開始
├── ダウンロード速度を測定
├── 速度に応じて品質調整
├── 遅い回線 → LOD低め
└── 速い回線 → LOD高め
```

# 実装のポイント

## 1. プログレッシブ表示

```
ユーザー体験を優先:
├── 「何も見えない」状態を避ける
├── 低品質でも即座に表示
├── バックグラウンドで品質向上
└── 読み込み中インジケーター表示
```

## 2. プリフェッチ

```
カメラ移動予測:
├── 移動方向を検出
├── 移動先のタイル/Gaussianを事前取得
├── 「カクつき」を防止
└── 帯域に余裕があるときに実行
```

## 3. キャッシュ戦略

```
キャッシュ:
├── Service Worker でオフライン対応
├── IndexedDB でローカル保存
├── メモリキャッシュ（LRU）
└── CDNエッジキャッシュ
```

## 4. メモリ管理

```
メモリ上限管理:
├── 最大メモリ使用量を設定
├── 古いGaussianをアンロード
├── LRU（Least Recently Used）方式
└── メモリ圧迫時は品質を下げる
```

# パフォーマンス指標

## 測定すべき指標

| 指標 | 目標値 | 測定方法 |
|------|--------|---------|
| 初期表示時間 | < 3秒 | Performance API |
| フレームレート | > 30 FPS | requestAnimationFrame |
| メモリ使用量 | < 200MB | performance.memory |
| 帯域使用量 | < 2MB/秒 | NetworkInformation API |

## 監視と改善

```
継続的な監視:
├── Real User Monitoring (RUM)
├── 遅いデバイスの特定
├── ボトルネックの分析
└── A/Bテストで改善検証
```

# まとめ

| 手法 | 特徴 | 適用シーン |
|------|------|-----------|
| LODストリーミング | 段階的品質向上 | 汎用的 |
| 視点ベース | メモリ効率最高 | 大規模シーン |
| タイルベース | CDN配信向き | 公開サービス |

**推奨アプローチ:**
1. LODストリーミングで初期表示を高速化
2. 視点ベースでメモリ効率を改善
3. タイルベースでCDN配信を最適化

**ストリーミングで、3DGSを誰もが快適に体験できる。**
